## R21 · 患者档案的"回响"缺失（新系统最大缺口）

**实据**：
- `patientType.ts` 35 种档案**零 `flagSet` / 零 `requireFlag`**（grep 计数 = 0）。
- `wardVisitEvent` / `socialEncounterEvent` 生成的 400+210 条事件**全部不设 flag**（`flagSet` 计数 = 0）。
- 对比：clinicEvent 至少设 `seen_${c.spec}` 被 difficult 事件消费——患者档案线连这一级的回响都没有。

**结论**：患者多样性目前只是"单次事件内的文本/选项多样性"（遇到谁 → 选项不同），
**没有"遇到之后"的延续**：你上次关照的那位独居老人、那个好诉的家属，下次不会回来。

**任务**：
- [ ] **P0** 病房互访设 `met_${arch.id}`，并新增"患者回声"事件（`requireFlag: met_xxx`）：
  出院患者回来复查/感谢/投诉——让"你管过的病人"真的会再次出现。
- [ ] 社会遭遇设 `met_${ch.id}` 之类 flag，部分人物可在后续阶段"再遇"（npcGen 已有确定性索引可复用）。
- [ ] 测试：`patient-diversity.spec.ts` 补断言——每个档案的 `met_` flag 都有 setter 与 consumer（沿用 no-dead-flag 约定）。

## R22 · 病房互访权重与手写优先的稀释

**实据**：
- 手写优先机制：`handPriority()` 默认 0.65，65% 概率先抽手写池，35% 回落到全池。
- 但**新增 400 条 ward + 210 条 social 全部是 `gen_`（生成事件），进的是"全池回落"那一支**。
- 实测职业阶段手写占比 8.6%，全池含生成事件后手写命中率 ≈ 68%——**手写叙事主线仍保得住** ✓
  但生成池从 ~4200 涨到 ~5660（+35%），同一季内"同一条生成事件被重复抽到"的概率上升。

**任务**：
- [ ] P2 用浏览器实测：跑满职业 24 季，统计生成事件标题去重率，若 < 60% 需给 gen 事件加 `once` 或提高去重
- [ ] P2 建立 `event-pool-diversity.spec.ts`：断言每阶段抽取 N 次后唯一事件比例 ≥ 阈值（防池子膨胀到"天天撞同一张卡"）

## R23 · 事件池规模与构建体积

**实据**：手写 330 + 生成 5660 ≈ **5990 条**；`dist` bundle 1.63MB（gzip 463KB）。
- 生成事件是运行时 `new` 出来的对象数组，不是序列化数据——构建体积只含模板代码，可接受。
- 但 `getAvailableEvents` 每回合对**全池 filter**（~6000 条 × 条件判断），职业期高频调用（hasStorylet/每帧提示/抽取）可能有微秒级开销。

**任务**：
- [ ] P3 性能：把 `getAvailableEvents` 的 stage 过滤改为按 stage 预索引（Map<stage, events>），避免每回合全池扫描
- [ ] P3 用 `performance.now` 实测职业期单次 drawStorylet 耗时，目标 < 2ms
